## Barrier B1 — No stable UI locator convention for new ERB/ViewComponent elements

| | |
|---|---|
| **Evidence** | ERB + ViewComponent UI layer confirmed in DEPENDENCIES.md (`view_component`, `turbo-rails`, `stimulus-rails`). CONVENTIONS.md documents no selector convention for test targeting (`data-testid`, `data-cy`, `aria-label` not mentioned). System tests use Capybara with no stated locator standard. |
| **Description** | When a new interactive or presentational element is added to an ERB template or ViewComponent, there is no project-wide convention that tells the author what stable identifier to place on it. Capybara system tests in `test/system/` must locate elements somehow; without a convention, authors fall back to CSS classes, element position, or text content — all fragile selectors that break on unrelated refactors. |
| **Signal** | A new ERB partial, `.html.erb` view, or `*_component.html.erb` template adds a button, form field, or interactive region that can only be located in a Capybara test by its generated text content, a Tailwind class, or positional selector (`.first`, `.last`, `nth-child`). |
| **Minimum fix** | Add a single `data-testid="<feature-name>"` attribute to the element (e.g., `data-testid="transaction-delete-btn"`). One attribute only. Do not add `id` attributes alongside it. Do not create a new component wrapper just to expose the identifier. |
| **Do NOT do** | Add both `data-testid` and `aria-label` "for good measure". Rename existing elements or restructure the component. Add Capybara-specific CSS classes. |
| **Blocked test** | A Capybara system test asserting that clicking the new delete button on a transaction removes the row cannot be written without a stable locator on that button. |

## Barrier B2 — No OpenAPI / contract file for the /api/v1/ REST namespace

| | |
|---|---|
| **Evidence** | ARCHITECTURE.md documents a live `/api/v1/` REST API namespace with Doorkeeper OAuth and Jbuilder JSON responses. TESTING.md explicitly states "No contract tests: No Pact or similar consumer-driven contract tests for the `/api/v1/` external API." No `openapi.yaml`, `.proto`, or AsyncAPI file found in `maybe/` directory listing. |
| **Description** | New route handlers and Jbuilder templates added to `app/controllers/api/v1/` have no schema entry that tests or clients can validate against. The shape of every response is defined implicitly by the Jbuilder template alone; there is no machine-readable contract a consumer can depend on or a test can assert against without hitting the full stack. |
| **Signal** | A new file added under `app/controllers/api/v1/` or `app/views/api/v1/` that introduces a new endpoint or changes a response field, with no corresponding entry in any schema or contract file in the repository. |
| **Minimum fix** | Add a minimal OpenAPI path entry (path + HTTP method + response fields) to a new `docs/api/openapi.yaml`, matching the style of any adjacent entries if the file already exists. Describe only the new endpoint — do not document the entire API surface in one pass. |
| **Do NOT do** | Refactor existing Jbuilder templates to generate the schema. Introduce a new contract format or tooling (e.g., rswag, apipie) without team agreement. Add client-side TypeScript types derived from the schema. |
| **Blocked test** | A test asserting that `GET /api/v1/accounts` returns a response conforming to the documented schema cannot be written without a schema to validate against. |

## Barrier B3 — Faraday HTTP client used inside model bodies with no substitution mechanism

| | |
|---|---|
| **Evidence** | `faraday` found in DEPENDENCIES.md as the HTTP client for external API calls. ARCHITECTURE.md shows `PlaidItem` calls the Plaid API via Faraday inside the model, and `app/models/provider/` wraps Synth and other providers. The "fat models" convention places this I/O directly inside model methods. VCR + WebMock are used in tests but require cassette recording for every new external call path. |
| **Description** | Methods in `app/models/provider/`, `app/models/plaid_item/`, and `app/models/exchange_rate/` issue Faraday requests from inside the method body. A test that wants to assert on the result of a new method must either record a VCR cassette (requiring a live API call or manual cassette authoring) or stub via WebMock — both of which are external setup steps invisible from the model code itself. If a new provider method is added without a cassette, the test hits the live API or raises `WebMock::NetConnectNotAllowedError`. |
| **Signal** | A new method in `app/models/provider/`, `app/models/plaid_item/`, `app/models/exchange_rate/`, or any model under `app/models/` that calls `Faraday.new(…).get(…)` or a provider connection method directly inside the method body, with no corresponding VCR cassette file in `test/vcr_cassettes/` and no `stub_request` call in its test. |
| **Minimum fix** | Add a VCR cassette for the new HTTP interaction: record it once with `VCR.use_cassette("provider/new_endpoint") { … }` wrapping the test call. Place the cassette in `test/vcr_cassettes/` following the naming convention of adjacent cassettes. One cassette per distinct HTTP interaction shape. |
| **Do NOT do** | Extract a Faraday client parameter across all provider models (breaks the fat-models convention). Introduce a HTTP client interface or repository layer. Add `WebMock.allow_net_connect!` in tests. |
| **Blocked test** | A unit test for a new `Provider::Synth#fetch_security_price` method cannot assert the returned price without either a VCR cassette or a WebMock stub, and the test will raise `NetConnectNotAllowedError` without one. |

## Barrier B4 — Time-dependent logic uses Time.current / Date.today with no injectable override

| | |
|---|---|
| **Evidence** | Ruby on Rails idiom (`Time.current`, `Date.today`, `Time.zone.now`) is the standard time source throughout the codebase. DEPENDENCIES.md shows no time-injection library (e.g., `timecop`, `ActiveSupport::Testing::TimeHelpers` — though Rails provides `travel_to` in tests). ARCHITECTURE.md notes balance calculation (`Balance::Syncer`) and period-based reporting (`Period` model) are date-sensitive. No explicit injection pattern for time is documented in CONVENTIONS.md. |
| **Description** | Methods that compute "current period", "days until", or "as of today" balances call `Time.current` or `Date.today` directly in the method body. Tests that want to assert date-sensitive behavior must use Rails' `travel_to` helper (available in `ActiveSupport::TestCase`) — but only if the test author knows to wrap the assertion in a `travel_to` block. New date-sensitive methods added without this pattern produce tests that pass today but fail on a different date or in CI at midnight. |
| **Signal** | A new method in `app/models/balance/`, `app/models/period.rb`, `app/models/income_statement/`, or any reporting model that calls `Time.current`, `Date.today`, or `Time.zone.now` directly in the method body, with no `travel_to` block in its corresponding test. |
| **Minimum fix** | Wrap the test assertion in `travel_to(Time.zone.parse("2024-01-15")) { … }` using Rails' built-in `travel_to` helper. Do not change the production code — `travel_to` is the Rails-idiomatic fix and requires no structural change. |
| **Do NOT do** | Introduce a clock parameter or `TimeProvider` object. Use `Timecop` (not in the project). Freeze time globally for a whole test file. |
| **Blocked test** | A test asserting that `Period.current_month.transactions_total` returns the correct sum for January 2024 cannot be written deterministically without `travel_to` wrapping the assertion. |

## Barrier B5 — Sidekiq jobs fire-and-forget from model callbacks with no testable completion handle

| | |
|---|---|
| **Evidence** | `sidekiq` and `sidekiq-cron` found in DEPENDENCIES.md. ARCHITECTURE.md documents `SyncAccountsJob`, `ImportDataJob`, and `CreateChatResponseJob` as background workers. The Plaid sync flow shows `after_commit_everywhere` callbacks triggering background work after DB commits. Job tests in `test/jobs/` are listed as "No (mocked)" for external deps — confirming jobs are tested in isolation, not end-to-end. |
| **Description** | When a model method (e.g., `PlaidItem#sync!`) enqueues a Sidekiq job via `SomeJob.perform_later(…)` or a callback, the caller has no handle to await or inspect the result. Tests that assert on the outcome of the job's work must either inline the job logic or explicitly call `perform_enqueued_jobs` / assert on enqueue with `assert_enqueued_with`. New model methods that trigger jobs without this pattern produce tests that pass vacuously — the job is enqueued but never executed in the test. |
| **Signal** | A new model method, callback, or `after_commit_everywhere` block that calls `SomeJob.perform_later(…)` or `SomeJob.perform_async(…)`, with a test that asserts on the post-job state of the database without an `assert_enqueued_with` assertion or an explicit inline job execution. |
| **Minimum fix** | In the test, assert that the job was enqueued with the correct parameters using `assert_enqueued_with(job: SomeJob, args: […])`, or inline the job execution with `perform_enqueued_jobs { trigger_the_action }`. Use whichever is already present in adjacent job tests in `test/jobs/`. |
| **Do NOT do** | Add polling or `sleep` calls in tests to wait for real Sidekiq execution. Switch to synchronous execution mode globally. Introduce a new queue abstraction. |
| **Blocked test** | A test asserting that calling `account.sync!` results in updated `Balance` records cannot verify job side-effects without either inlining job execution or asserting on enqueue. |

## Barrier B6 — Rails.application.config.app_mode read directly inside model/controller bodies

| | |
|---|---|
| **Evidence** | ARCHITECTURE.md documents dual app modes (`managed` vs `self_hosted`) controlled by `Rails.application.config.app_mode`, with the note that this "adds conditional logic throughout" models and controllers. `ClimateControl` is present in the test suite (DEPENDENCIES.md) for ENV overrides, and `test_helper.rb` provides a `with_self_hosting` helper that stubs `Rails.configuration.app_mode` — confirming direct config reads exist in production code. |
| **Description** | New conditional branches keyed on `Rails.application.config.app_mode` (or equivalent mode checks) are resolved at call time against the global Rails config. While `with_self_hosting` exists in `test/test_helper.rb` as a stub helper, authors of new mode-gated code must know to wrap their test in that helper — it is not enforced. A test written without `with_self_hosting` will always test only the default mode, leaving the other branch uncovered. |
| **Signal** | A new `if Rails.application.config.app_mode.managed?` or `if Rails.application.config.app_mode.self_hosted?` branch in `app/models/` or `app/controllers/`, with a test that does not use the `with_self_hosting` helper (or equivalent stub) to exercise the alternate branch. |
| **Minimum fix** | Write two test cases for any mode-gated branch: one without `with_self_hosting` (tests managed behavior) and one wrapped in `with_self_hosting { … }` (tests self-hosted behavior). The `with_self_hosting` helper is already defined in `test/test_helper.rb` — use it directly. |
| **Do NOT do** | Introduce a new config injection parameter. Create a separate test environment for each mode. Add `Rails.application.config.app_mode =` assignments in tests (modifies global state). |
| **Blocked test** | A test asserting that the self-hosted Stripe billing bypass works correctly cannot verify the `self_hosted` branch without `with_self_hosting` wrapping. |

## Barrier B7 — New models/associations may lack fixture coverage in test/fixtures/

| | |
|---|---|
| **Evidence** | TESTING.md documents that all tests load `fixtures :all` from `test/fixtures/` and that fixtures are intentionally minimal (2–3 per model). TESTING.md also lists "VCR cassettes may drift" as a known gap, and the fixture-minimal policy is explicit in CLAUDE.md ("Keep fixtures minimal (2-3 per model for base cases)"). New models added to `app/models/` require a corresponding YAML fixture file before any test can reference them by fixture name. |
| **Description** | When a new ActiveRecord model is added (or a new association is introduced on an existing model), the `test/fixtures/` directory will not automatically contain the required YAML file. Any test that calls `fixtures :all` and then references a fixture name from the new model will raise `StandardError: No fixture file found for …`. This is a mechanical gap — not a design problem — but it blocks the first test for every new model. |
| **Signal** | A new file in `app/models/` (e.g., `app/models/budget_allocation.rb`) with no corresponding `test/fixtures/budget_allocations.yml`, and a test in `test/models/` that tries to reference `budget_allocations(:one)`. |
| **Minimum fix** | Add `test/fixtures/<table_name>.yml` with 2–3 minimal records matching the schema of the new model. Follow the format and column names of any adjacent fixture file exactly. Add only the columns required for the test paths being written — do not pre-populate every column. |
| **Do NOT do** | Switch to FactoryBot or any factory-based strategy (explicitly forbidden by CLAUDE.md). Add a factory fallback alongside the existing fixture strategy. Create fixtures with more than 3 records unless a specific test requires it. |
| **Blocked test** | A test for a new `BudgetAllocation` model cannot use `budget_allocations(:one)` until `test/fixtures/budget_allocations.yml` exists with at least one named record. |

## Decision rule

A barrier entry justifies a change only when a concrete, nameable test is blocked.
If the blocked test cannot be named in one sentence, discard the change.
When in doubt, discard.
