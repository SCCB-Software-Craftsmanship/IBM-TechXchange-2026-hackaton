# testability-heuristics

Reads the project context produced by `analyze-codebase` and derives a set of concrete
testability barriers grounded in what this repository actually does. Every barrier in the
output must be justified by specific evidence found in the project — a library name, a
pattern in test files, an architectural decision. If no evidence exists for a barrier
shape, that barrier does not appear in the output.

The result is `.bob/HEURISTICS.md`, which `testability-prep` reads during barrier scanning.
It must never need further interpretation.

If `analyze-codebase` has not been run yet, this skill infers the project context directly
from source files. It never prompts the user for information it can discover itself.

---

## Non-negotiable rule

Every barrier entry written to `.bob/HEURISTICS.md` must include an **Evidence** field
that names the specific artifact found in the project context that confirms this barrier
shape exists here. A barrier with no evidence must not appear in the output.

---

## Step-by-step process

### Step 1 — Gather project context

Attempt to read each of the following files in order. Record what each reveals about
the project's language, framework, dependencies, test helpers, and architecture.

**From `.bob/` (preferred — generated by `analyze-codebase`):**

1. Call `read_file` on `.bob/TESTING.md`. If not found, try `TESTING.md`. Record: test
   framework, helper patterns, async utilities, teardown idioms.
2. Call `read_file` on `.bob/CONVENTIONS.md`. If not found, try `CONVENTIONS.md`. Record:
   selector/identifier convention, naming patterns.
3. Call `read_file` on `.bob/DEPENDENCIES.md`. If not found, try `DEPENDENCIES.md`. Record:
   HTTP client, database client, time/UUID utilities, async primitives, UI framework.
4. Call `read_file` on `.bob/ARCHITECTURE.md`. If not found, try `ARCHITECTURE.md`. Record:
   DI style, module structure, config loading pattern, contract files present.

**If none of the above exist (no `analyze-codebase` run):**

5. Call `glob` with `**/*.test.*`, `**/*.spec.*`, `**/*_test.*` — pick up to 5 results and
   call `read_file` on each with range `1-60` to infer test framework and helpers.
6. Call `glob` with `package.json`, `go.mod`, `requirements*.txt`, `Pipfile`, `Cargo.toml`,
   `pom.xml` — read each to identify language and dependency names.
7. Call `list_files` on the workspace root (non-recursive) to confirm primary language and
   check for contract files (`openapi.yaml`, `*.proto`, `asyncapi.yaml`).

After this step, produce an internal **evidence inventory** — a flat list of concrete
facts found, for example:

```
- UI framework: React 18 (from package.json)
- HTTP client: axios 1.x (from package.json)
- DB client: prisma (from package.json)
- Time source: Date.now (inferred from JS/TS language)
- Selector convention: data-testid (from CONVENTIONS.md)
- Test framework: jest + @testing-library/react (from TESTING.md)
- DI style: default-parameter injection (from ARCHITECTURE.md)
- Contract file: none found
- Async patterns: no fire-and-forget detected
- Global state: no module-level mutable state detected
```

This inventory is internal — it drives Step 3 but is not written to the output.

---

### Step 2 — Load the reasoning guide

Call `read_file` on `SKILLS/testability-heuristics/heuristics-reference.md` to load the
four diagnostic dimensions and their evidence patterns.

---

### Step 3 — Derive barriers from evidence

For each diagnostic dimension in the reasoning guide, check the evidence inventory from
Step 1. A barrier is produced **only** when a specific item in the inventory matches an
evidence pattern in the guide.

Work through the dimensions in order:

**Dimension 1 — Observability:**
- If a UI framework is present → check for evidence pattern 1-A (locator convention).
  Produce barrier if UI framework confirmed.
- If route handlers, emitters, or producers exist in the project → check for evidence
  pattern 1-B (contract file). Produce barrier only if no contract file found.

**Dimension 2 — Controllability:**
- If an HTTP client, DB client, or filesystem API is in the evidence inventory → produce
  barrier from evidence pattern 2-A (I/O boundary).
- If a time API or ID generator is in the evidence inventory → produce barrier from
  evidence pattern 2-B (time/randomness).
- If deferred execution (timers, background workers, queues) is in the evidence inventory
  → produce barrier from evidence pattern 2-C (async fire-and-forget).
- If direct environment or global config access is in the evidence inventory → produce
  barrier from evidence pattern 2-D (config coupling).

**Dimension 3 — Isolation:**
- If module-level mutable variables, registries, or caches are detected → produce barrier
  from evidence pattern 3-A (global state).
- If module-level side effects at load/construction time are detected → produce barrier
  from evidence pattern 3-B (init side effects).
- If the project's test data strategy requires artifacts that new code paths may not
  have covered → produce barrier from evidence pattern 3-C (missing fixture).

**Dimension 4 — Determinism:**
- If a non-determinism source is found that does not map to 2-B or 3-A → derive a new
  barrier specific to that source.

For each produced barrier:
- Write it in fully concrete, project-specific terms (real library names, real function
  names, real file paths).
- Assign it the next local number (B1, B2, B3…).
- Include an **Evidence** field citing the specific inventory item that triggered it.

If an evidence item is not present in the inventory, produce nothing for that pattern.
Do not produce a barrier and note it as "not applicable" — silence is correct.

---

### Step 4 — Write `.bob/HEURISTICS.md`

Write the file using `write_file`. The file must contain:

**Header block:**

```
# Project Heuristics

Generated by: testability-heuristics
Detected stack: <language> / <framework if applicable>
Context sources consulted: <comma-separated list of files actually read in Step 1>
Date: <today's date in YYYY-MM-DD format>

This file is the project-derived barrier checklist for `testability-prep`.
Every entry is grounded in evidence found in this repository.
Do not edit manually — re-run `/testability-heuristics` to regenerate.
```

**Barrier entries** — one section per derived barrier:

```markdown
## Barrier B<N> — <title describing the specific problem in this project>

| | |
|---|---|
| **Evidence** | <what was found: library name, pattern, file, absence of file> |
| **Description** | <what the barrier is, in project-specific terms> |
| **Signal** | <what a reviewer would see in the diff that confirms this barrier> |
| **Minimum fix** | <the concrete action: real function name, real parameter name> |
| **Do NOT do** | <project-specific anti-patterns> |
| **Blocked test** | <one sentence: the specific test that is currently impossible> |
```

**Decision rule** (written verbatim at the end of the file):

```markdown
## Decision rule

A barrier entry justifies a change only when a concrete, nameable test is blocked.
If the blocked test cannot be named in one sentence, discard the change.
When in doubt, discard.
```

---

## On re-runs

If `.bob/HEURISTICS.md` already exists, overwrite it completely. Do not merge — a full
regeneration ensures the output reflects the current project state.
