# scan-test-suites

Reads the project's existing test files and configuration, applies the reasoning guide in
`SKILLS/scan-test-suites/test-suite-reader.md` to extract structural patterns, and writes
`.bob/TEST-SUITES.md` — a self-contained description of how the test suite is built.

Every section in the output must be grounded in specific evidence found in the project's
test files. A dimension with no evidence produces no section. Silence is correct.

The result is `.bob/TEST-SUITES.md`, which downstream skills (e.g. `testability-heuristics`,
`generate-tests`) consume without further interpretation.

---

## Non-negotiable rule

Every section written to `.bob/TEST-SUITES.md` must include an **Evidence** field that names
the specific file(s), line(s), or pattern(s) found in the project that confirm the observation.
A section with no evidence must not appear in the output.

---

## Step-by-step process

### Step 1 — Gather project context

Attempt to read each of the following in order. Record what each reveals about the project's
test framework, test organisation, and dependencies.

**From `.bob/` (preferred — generated by `analyze-codebase`):**

1. Call `read_file` on `.bob/TESTING.md`. If not found, try `TESTING.md`. Record: test
   framework name, test runner command, any helper patterns or custom utilities mentioned.
2. Call `read_file` on `.bob/DEPENDENCIES.md`. If not found, try `DEPENDENCIES.md`. Record:
   assertion libraries, mocking libraries, HTTP interception libraries, fixture helpers.
3. Call `read_file` on `.bob/CONVENTIONS.md`. If not found, try `CONVENTIONS.md`. Record:
   any stated test file naming or location convention.

**If none of the above exist (no `analyze-codebase` run):**

4. Call `glob` with pattern `package.json` — call `read_file` on the result to identify the
   language, test runner (look in `scripts`), and testing libraries (look in `devDependencies`).
   Also try `pyproject.toml`, `go.mod`, `Cargo.toml`, `pom.xml` if `package.json` is not found.
5. Call `glob` with patterns `jest.config.*`, `vitest.config.*`, `pytest.ini`, `setup.cfg`,
   `playwright.config.*`, `cypress.config.*` — call `read_file` on each match found.

After this step, record an internal **context summary** — a short flat list of confirmed facts,
for example:

```
- Test framework: Jest (from package.json devDependencies)
- Test runner command: npx jest (from package.json scripts.test)
- Mocking library: jest built-in (no separate mock library found)
- HTTP interception: msw 2.x (from package.json devDependencies)
- Assertion library: Jest expect (built-in)
- Location convention: not stated in CONVENTIONS.md — to be inferred from files
```

This summary is internal — it drives Step 3 but is not written to the output.

---

### Step 2 — Load the reasoning guide

Call `read_file` on `SKILLS/scan-test-suites/test-suite-reader.md` to load the six reading
dimensions and the derivation instruction.

---

### Step 3 — Read representative test files

Call `glob` with each of the following patterns in order. Collect all matches:

- `**/*.test.ts`, `**/*.test.js`, `**/*.test.tsx`
- `**/*.spec.ts`, `**/*.spec.js`, `**/*.spec.tsx`
- `**/*_test.go`, `**/*_test.py`, `**/*Test.java`, `**/*_spec.rb`
- `**/__tests__/**/*`, `**/tests/**/*`, `**/test/**/*`

From the collected matches, select a representative sample — up to **8 files** — that covers
different levels of the project if multiple levels exist (unit, integration, e2e). Prefer
variety over exhaustiveness: pick the files that look most different from each other.

For each selected file:

- Call `read_file` with range `1-80` to read the first 80 lines. This is sufficient to see
  the imports, test framework syntax, describe/it structure, and first test body.
- If the first 80 lines do not contain any test body (e.g. all imports and setup), call
  `read_file` again with range `81-160` to reach the first actual test.

Then apply the reasoning guide loaded in Step 2. For each of the six reading dimensions,
check the collected file content and context summary for evidence. When evidence is found,
record the observation in project-specific terms: real file names, real function names, real
library names.

If `grep` would reveal a pattern faster than reading files (e.g. checking whether
`jest.mock` appears anywhere in the test tree), call `grep` with the pattern and the
`tests/` or `src/` directory rather than reading more files.

---

### Step 4 — Write `.bob/TEST-SUITES.md`

Call `write_file` to write the file. The file must contain:

**Header block:**

```markdown
# Test Suites

Generated by: scan-test-suites
Detected stack: <language> / <test framework>
Context sources consulted: <comma-separated list of files actually read in Steps 1 and 3>
Date: <today's date in YYYY-MM-DD format>

This file is the project-derived test suite description for downstream skills.
Every section is grounded in evidence found in this repository's test files.
Do not edit manually — re-run `/scan-test-suites` to regenerate.
```

**Observation sections** — one per reading dimension where evidence was found:

```markdown
## <Dimension title — e.g. "Anatomy", "File Layout", "Setup and Teardown", "Seam Patterns", "Assertion Style", "Coverage Shape">

| | |
|---|---|
| **Evidence** | <specific files or patterns that confirmed this observation> |
| **Observation** | <what was found, in project-specific terms> |
| **Convention** | <the rule a new test must follow to match the existing suite> |
| **What it reveals** | <what this tells a downstream skill about how to write or locate tests> |
```

**Only include a section when the Evidence field can be filled with a named file or pattern.**
If evidence is absent for a dimension, that section does not appear. Do not write "Not found"
or "N/A" — silence is the correct output.

---

## On re-runs

If `.bob/TEST-SUITES.md` already exists, overwrite it completely. Do not merge — a full
regeneration ensures the output reflects the current project state.
