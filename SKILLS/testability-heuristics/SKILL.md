# testability-heuristics

Reads the project context already produced by `analyze-codebase` and translates the universal
`heuristics-reference.md` into a concrete, project-adapted `.bob/HEURISTICS.md`. Every abstract
term in the universal reference ("the I/O client", "the time source") is replaced with the
real library name, idiom, or file path found in this repository. The result is the file that
`testability-prep` reads during barrier scanning — it must never need further interpretation.

If `analyze-codebase` has not been run yet, this skill infers the project context directly
from the source files. It never prompts the user for information it can discover itself.

---

## Non-negotiable rule

The generated `.bob/HEURISTICS.md` must contain **only adapted barriers** — every Description,
Signal, and Minimum fix row must reference real, project-specific terms. A barrier entry that
still contains abstract placeholders ("the I/O client", "the time source") must not appear in
the output. Either adapt it fully or omit it with a reason in the "Skipped barriers" section.

---

## Step-by-step process

### Step 1 — Gather project context

Attempt to read each of the following files, in the order listed. Record what each file
reveals about language, framework, test helpers, dependency names, and architectural patterns.

**From `.bob/` (preferred — generated by `analyze-codebase`):**

1. Call `read_file` on `.bob/TESTING.md`. If not found, try `TESTING.md`. Record: test
   framework name, test helper patterns, async test utilities, teardown idioms.
2. Call `read_file` on `.bob/CONVENTIONS.md`. If not found, try `CONVENTIONS.md`. Record:
   selector/identifier convention, naming patterns, any test-infrastructure conventions.
3. Call `read_file` on `.bob/DEPENDENCIES.md`. If not found, try `DEPENDENCIES.md`. Record:
   HTTP client library, database client library, time/UUID utilities, async primitives.
4. Call `read_file` on `.bob/ARCHITECTURE.md`. If not found, try `ARCHITECTURE.md`. Record:
   dependency injection style, module structure, config loading pattern.

**If none of the above files exist (no `analyze-codebase` run):**

5. Call `glob` with `**/*.test.*`, `**/*.spec.*`, `**/*_test.*` — pick up to 5 results and
   call `read_file` on each with range `1-60` to infer test framework and helper patterns.
6. Call `glob` with `package.json`, `go.mod`, `requirements*.txt`, `Pipfile`, `Cargo.toml`,
   `pom.xml` — read each found file to identify language and dependency names.
7. Call `list_files` on the workspace root (non-recursive) to understand top-level structure
   and confirm the primary language from directory layout.

After this step, record a **context summary** (internal, not written to output):
- Primary language and version (if determinable).
- UI layer present? (yes/no and framework name if yes).
- Primary I/O client(s) name(s).
- Time/randomness source(s) in use.
- Async primitive(s) in use.
- Config/environment access pattern.
- Test framework and key helpers.
- DI / constructor injection style (if any).

### Step 2 — Load the universal reference

Call `read_file` on `SKILLS/testability-heuristics/heuristics-reference.md` to load all
nine barriers (A1–A9) with their Adaptation hint rows.

### Step 3 — Adapt each barrier

Process barriers A1 through A9 in order. For each barrier:

1. **Read the Adaptation hint row.** It tells you exactly what project-specific information
   to substitute into the Description, Signal, and Minimum fix rows.
2. **Apply the substitutions** using the context summary from Step 1:
   - Replace every abstract term with the concrete project equivalent.
   - Rewrite the Signal row so it describes a pattern a reviewer would actually see in *this*
     project's diff (e.g. "a new `axios.get(...)` call inside the function body" rather than
     "an I/O call initiated inside the function body").
   - Rewrite the Minimum fix row so it names the concrete action (e.g. "pass `query =
     db.query.bind(db)` as a default parameter" rather than "accept the I/O boundary as a
     parameter").
   - The Blocked test example may be updated to use project-specific terminology but its
     structure (one sentence naming the specific test that is blocked) must be preserved.
3. **Decide: include or skip.**
   - **Include** the barrier if the project has patterns or dependencies that could plausibly
     exhibit it (e.g. include A1 only if a UI layer is present; include A3 if the project has
     I/O client dependencies; include A6 if async primitives are in use).
   - **Skip** the barrier if there is no plausible manifestation in this project. Record the
     skipped barrier ID and a one-line reason (e.g. "A1 skipped — no UI layer detected").
4. **Drop the Adaptation hint row** from the adapted entry — it must not appear in the output.

### Step 4 — Write `.bob/HEURISTICS.md`

Write the generated file using `write_file` to `.bob/HEURISTICS.md`. The file must contain:

**Header block** (first section, before any barrier):

```
# Project Heuristics

Generated by: testability-heuristics
Detected stack: <language> / <framework if applicable>
Context sources consulted: <comma-separated list of files actually read in Step 1>
Date: <today's date in YYYY-MM-DD format>

This file is the project-adapted barrier checklist for `testability-prep`.
Every entry has been concretized for this repository. Do not edit manually —
re-run `/testability-heuristics` to regenerate after project dependencies change.
```

**Adapted barrier entries** (one section per included barrier, same two-column table
format as `heuristics-reference.md`, with rows: Description, Signal, Minimum fix,
Do NOT do, Blocked test):

```markdown
## Barrier <ID> — <adapted title>

| | |
|---|---|
| **Description** | <project-specific description> |
| **Signal** | <project-specific signal — what the reviewer would see in the diff> |
| **Minimum fix** | <project-specific fix — naming the real library/function/pattern> |
| **Do NOT do** | <project-specific anti-patterns> |
| **Blocked test** | <one sentence naming the specific test that is blocked> |
```

**Quick-reference decision table** (copy verbatim from `heuristics-reference.md`, removing
the "Adapt using Adaptation hint →" prefix since adaptation is already done).

**Skipped barriers section** (at the end, only if any barriers were skipped):

```markdown
## Skipped barriers

| Barrier | Reason |
|---|---|
| A1 | No UI layer detected in this project. |
| A6 | No async operations detected in dependencies or source patterns. |
```

---

## On re-runs

If `.bob/HEURISTICS.md` already exists, overwrite it completely. Do not merge or diff — a
full regeneration ensures the output reflects the current project state.
